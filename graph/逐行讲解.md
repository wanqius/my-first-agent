## 逐行拆解

> **空行不单独讲解**，所以下面的行号会有跳跃（比如没有第 3~4 行、第 7~8 行）。

### 第 1 行

```python
from typing import TypedDict
```

**在干什么**：从 Python 标准库 `typing` 里取出 `TypedDict` 这个名字，后面第 5 行要用。

**为什么**：`TypedDict` 是"带类型的字典"的声明工具。**它是自带的，不用 pip 装。**

---

### 第 2 行

```python
from langgraph.graph import StateGraph, START, END
```

**在干什么**：一次从 `langgraph.graph` 里取三样东西。

| 名字           | 是什么       | 用在哪    |
| ------------ | --------- | ------ |
| `StateGraph` | 画布类（用来建图） | 第 13 行 |
| `START`      | 入口标记（常量）  | 第 15 行 |
| `END`        | 出口标记（常量）  | 第 16 行 |

**要注意**：`START` / `END` 是**变量名，不是字符串**。写成 `"START"` 就变成普通文本，框架不认识。

---

### 第 5 行

```python
class State(TypedDict):
```

**在干什么**：定义一个类，名叫 `State`，父类是 `TypedDict`。

**为什么**：这是**"记录本的结构说明书"**——告诉框架"整张图里流动的数据长什么样"。

**要注意三件事**：

1. **这一行不执行任何逻辑**，只是声明
2. 末尾的**冒号不能少**，它表示"下面是类体"
3. 括号里的 `TypedDict` 是**父类**，不是字段

---

### 第 6 行

```python
    n: int
```

**在干什么**：声明 `State` 里有一个字段叫 `n`，类型是整数。

**为什么**：有了它，框架和你都能知道"数据里应该有个 n"。

**最容易误解的一点**：

> **这是类型标注，不是赋值。**  
> 它**不创建 `n`，也不给 `n` 一个初始值**。  
> 真正给 `n` 赋值的地方，是第 20 行的 `{"n": 0}`。

---

### 第 9 行

```python
def add_one(state):
```

**在干什么**：定义一个函数，名字叫 `add_one`，收**一个参数** `state`。

**为什么**：**这个函数就是一个"节点"**——图上那个圈，背后就是这个函数。

**要注意**：`state` 不用你手动传，**框架会把它当前持有的记录本递进来**。

---

### 第 10 行

```python
    return {"n": state["n"] + 1}
```

**拆开看这三步**：

| 片段           | 在干什么              |
| ------------ | ----------------- |
| `state["n"]` | 从字典里**取出** `n` 的值 |
| `+ 1`        | 加一                |
| `{"n": ...}` | 用结果**组成一个新字典**返回  |

**在干什么**：把 `n` 加一，然后把这个改动交回去。

**最关键的一条**：

> **只返回你要改的字段，不要 `return state`。**  
> 框架会把返回的字典**合并**进原 state，其他字段自动保留（第五节实验 4 实测）。

---

### 第 13 行

```python
builder = StateGraph(State)
```

**拆开看**：

| 片段                | 在干什么            |
| ----------------- | --------------- |
| `StateGraph(...)` | 创建一个**空的画布对象**  |
| 括号里的 `State`      | 告诉画布"数据按这个规格来"  |
| `builder =`       | 给这个画布起个名字，后面都用它 |

**最容易错的一点**：

> 传的是 **`State`（类本身，不带括号）**。  
> 写成 `StateGraph(State())` 就变成"创建一个实例传进去"，语义完全不同，会报错。

---

### 第 14 行

```python
builder.add_node("add_one", add_one)
```

**在干什么**：往画布上**放一个节点**。

**两个参数必须分清**：

| 位置    | 值           | 是什么            | 作用               |
| ----- | ----------- | -------------- | ---------------- |
| 第 1 个 | `"add_one"` | **名字**（字符串）    | 图上显示、路由目标、日志里都用它 |
| 第 2 个 | `add_one`   | **函数本身**（不带括号） | 真正被执行的代码         |

**这一行是本篇最容易错的地方**：

```python
builder.add_node("add_one", add_one)    # ✅ 传函数
builder.add_node("add_one", add_one())  # ❌ 传的是"调用结果"
```

> 你在阶段 2 踩过同一个坑：`print(count_words)` 打印出 `<function ... at 0x...>`。  
> **函数不带括号 = 这个东西本身；带括号 = 现在就用它。**

---

### 第 15 行

```python
builder.add_edge(START, "add_one")
```

**在干什么**：画一条边，**从入口指向 `add_one`**。

**为什么必须有**：没有这条边，图就没有起点。

**实测后果**：删掉这一行，`compile()` 会直接抛

```
ValueError: Graph must have an entrypoint: add at least one edge from START to another node
```

---

### 第 16 行

```python
builder.add_edge("add_one", END)
```

**在干什么**：画一条边，**从 `add_one` 指向出口**。

**为什么**：表示"这个节点干完就结束"。

**补充**：实测**删掉它也能跑**（节点执行完自然结束），但显式写出来，读代码的人一眼知道流程在哪停。

---

### 第 18 行

```python
graph = builder.compile()
```

**在干什么**：把草图**变成可执行对象**。

**它做三件事**：

| # | 做什么    | 说明                            |
| - | ------ | ----------------------------- |
| 1 | **校验** | 检查结构合法（比如有没有入口）               |
| 2 | **拍快照** | 把当时的节点表和边表固化成执行计划 |
| 3 | **产出** | 返回一个能 `.invoke()` 的对象         |

**记住这句话**：**画图 ≠ 能跑。`compile()` 之前，`builder` 只是草稿。**

---

### 第 20 行

```python
print(graph.invoke({"n": 0}))
```

**拆开看**：

| 片段             | 在干什么                      |
| -------------- | ------------------------- |
| `{"n": 0}`     | **初始 state**——图开始跑时手里拿的数据 |
| `.invoke(...)` | **同步执行**整张图，一直到 `END`     |
| `print(...)`   | 打印**返回值**                 |

**最容易误解的一点**：

> `invoke` 返回的是**执行结束后的整个 state**，**不是**节点函数返回的那个小字典。  
> 所以输出是 `{'n': 1}`，而不是 `{"n": 1}` 这个"局部改动"。

---

## 三个最容易搞错的地方（汇总）

| # | 坑                         | 正确做法                        |
| - | ------------------------- | --------------------------- |
| 1 | 以为 `n: int` 是赋值           | 它只是声明；赋值在第 20 行的 `{"n": 0}` |
| 2 | `add_node` 传了 `add_one()` | 传 `add_one`（不带括号）           |
| 3 | 以为 `compile()` 可有可无       | 没有它，图跑不起来                   |

# 二、`02_loop.py`：把直线接成圈

## 与 `01_hello.py` 的差别只有三处

| 位置             | 变化                                                                    |
| -------------- | --------------------------------------------------------------------- |
| 第 10 行         | 节点里**多了一行 print**（日志）                                                 |
| 第 14~17 行      | **新增判断函数** `should_continue`                                          |
| 第 22 / 24~28 行 | **删掉** `add_edge("add_one", END)`，**换成** `add_conditional_edges(...)` |

其余 1~~9、11~~13、18~22、30、32 行与 `01` 完全相同，不再重复。

## 完整代码（带行号）

```python
 1  from typing import TypedDict
 2  from langgraph.graph import StateGraph, START, END
 3
 4
 5  class State(TypedDict):
 6      n: int
 7
 8
 9  def add_one(state):
10      print("  [节点] n =", state["n"], "→", state["n"] + 1)
11      return {"n": state["n"] + 1}
12
13
14  def should_continue(state):
15      if state["n"] < 3:
16          return "again"
17      return "done"
18
19
20  builder = StateGraph(State)
21  builder.add_node("add_one", add_one)
22  builder.add_edge(START, "add_one")
23
24  builder.add_conditional_edges(
25      "add_one",
26      should_continue,
27      {"again": "add_one", "done": END},
28  )
29
30  graph = builder.compile()
31
32  print(graph.invoke({"n": 0}))
```

---

## 逐行拆解（只讲新增 / 改动的行）

### 第 10 行

```python
    print("  [节点] n =", state["n"], "→", state["n"] + 1)
```

**在干什么**：在节点里打一行日志。

**拆开看**：`print` 用**逗号**分隔多个值，输出时会**自动加空格**连起来。

**为什么这行重要**：

> 没有它，你只能看到最后结果 `{'n': 3}`——**看不到"节点跑了 3 次"**。  
> 这一行是"可观测性"的最小形态：**让循环的每一圈都留下痕迹**。

---

### 第 11 行

```python
    return {"n": state["n"] + 1}
```

**在干什么**：把改动交回给框架。

**和第 10 行的分工**：

| 行               | 给谁看           |
| --------------- | ------------- |
| 第 10 行 `print`  | **给人看**（日志）   |
| 第 11 行 `return` | **给框架看**（数据流） |

两者不能互相替代。

---

### 第 14 行

```python
def should_continue(state):
```

**在干什么**：定义一个**判断函数**（也叫路由函数）。

**它和节点的区别**：

|      | 节点          | 判断函数        |
| ---- | ----------- | ----------- |
| 收到什么 | `state`     | `state`     |
| 返回什么 | **一个 dict** | **一个字符串标签** |
| 谁调用它 | 框架按边执行      | 框架在"选路"时调用  |

**它不在图上是一个圈**——它只是节点旁边那个"路牌"。

---

### 第 15 行

```python
    if state["n"] < 3:
```

**在干什么**：判断"还没到 3 吗"。

**为什么是 `<` 而不是 `<=`**：想让 n 到 3 就停，所以条件是"小于 3 才继续"。

---

### 第 16 行

```python
        return "again"
```

**在干什么**：返回**标签字符串** `"again"`，意思是"再来一圈"。

**两个要注意**：

1. **返回的是字符串，不是 `True`**。写 `return True` 会找不到映射
2. **缩进比 `if` 多 4 格**——它在 `if` 里面，只在条件成立时执行

---

### 第 17 行

```python
    return "done"
```

**在干什么**：条件不成立时走到这里，返回 `"done"`。

**注意缩进**：它和 `if` 对齐（4 格），**在 `if` 外面**——所以条件不成立时必然执行到它。

---

### 第 22 行

```python
builder.add_edge(START, "add_one")
```

**和 `01` 第 15 行完全一样**：入口 → `add_one`。

**但要特别注意**：这里**没有** `add_edge("add_one", END)` 了。因为 `add_one` 的出口改由"条件边"决定——**一个节点不能同时有固定出口和条件出口**。

---

### 第 24~28 行

```python
builder.add_conditional_edges(
    "add_one",
    should_continue,
    {"again": "add_one", "done": END},
)
```

**在干什么**：画一条**条件边**（本质是"路牌 + 路由表"）。

**为什么占了 5 行**：只是**参数分行写**——括号里的换行不影响语法，纯粹为了好读（一个参数一行，改起来不容易漏逗号）。

**三个参数逐个说**：

#### 第 25 行 · 参数①

```python
    "add_one",
```

**从哪个节点出发**。必须是已经 `add_node` 过的名字（这里是字符串，和 `add_node` 的第 1 个参数对应）。

#### 第 26 行 · 参数②

```python
    should_continue,
```

**判断函数**（**不带括号**）。框架会在合适时机调用它，把当前 `state` 传进去。

> 又是那个规律：**传函数本身，不传调用结果。**

#### 第 27 行 · 参数③

```python
    {"again": "add_one", "done": END},
```

**映射表**：左边是"判断函数返回的标签"，右边是"应该去哪"。

| 键（标签）     | 值（目标）       | 含义                        |
| --------- | ----------- | ------------------------- |
| `"again"` | `"add_one"` | 说 again → **回到自己**（这就是循环） |
| `"done"`  | `END`       | 说 done → 结束               |

**注意右边两种写法**：

- `"add_one"` 是**字符串**（节点名）
- `END` 是**常量**（不加引号）

---

### 第 28 行

```python
)
```

**结束这次调用**。括号配对：第 24 行开，第 28 行关。

---

## 为什么判断函数返回"字符串"而不是 `True/False`

因为**标签可以有很多个**：

```python
{"again": "add_one", "done": END, "need_tool": "tool_node", "need_human": "wait_node"}
```

而 `if/else` 只能表达两条路。

> **这是 LangGraph 能画复杂流程的根源**：它问的不是"是 / 否"，而是"**去哪**"。  
> 等你写真正的 Agent，判断函数会返回 `"call_tool"` / `"answer"` / `"give_up"` 三种标签。

# 三、运行时序

## 01（直线，1 圈）

| 步 | 发生什么                                |
| - | ----------------------------------- |
| 1 | `invoke({"n": 0})` 把初始 state 交给图    |
| 2 | 从 `START` 出发，沿边到 `add_one`          |
| 3 | 执行 `add_one`：读到 `n=0`，返回 `{"n": 1}` |
| 4 | 框架把 `{"n": 1}` **合并**进 state        |
| 5 | 沿边到 `END`，结束                        |
| 6 | 返回最终 state `{'n': 1}`               |

## 02（循环，3 圈）

| 圈 | 进入节点时 n | 节点返回 | 判断函数算出                 | 去哪           |
| - | ------- | ---- | ---------------------- | ------------ |
| 1 | 0       | 1    | `1 < 3` → `"again"`    | 回到 `add_one` |
| 2 | 1       | 2    | `2 < 3` → `"again"`    | 回到 `add_one` |
| 3 | 2       | 3    | `3 < 3` 不成立 → `"done"` | `END`        |

**输出**：

```
  [节点] n = 0 → 1
  [节点] n = 1 → 2
  [节点] n = 2 → 3
{'n': 3}
```

# 四、五个核心概念

| 概念          | 一句话                  | 手写 `agent.py` 对应          |
| ----------- | -------------------- | ------------------------- |
| **State**   | 节点间流动的记录本（结构要声明）     | `messages` 列表             |
| **Node**    | 收 state、回 dict 的普通函数 | `ask()` / `get_today()`   |
| **Edge**    | 下一步去哪（直线 or 条件）      | `if/elif` 分发              |
| **compile** | 校验 + 锁定 + 变成可执行      | 无（手写没这一步）                 |
| **invoke**  | 喂初始 state，跑一整轮       | `for step in range(1, 4)` |

# 五、改一处会怎样（全部实机运行所得）

| 改动                                          | 实测结果                                                                                                          |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 删掉 `add_edge(START, "add_one")`             | **compile 时报错**：`ValueError: Graph must have an entrypoint: add at least one edge from START to another node` |
| 删掉 `add_edge("add_one", END)`（节点没有出口）       | **compile 通过，运行也正常**：节点执行 1 次后自然结束，返回 `{'n': 1}`。**框架不校验"死路"**                                                |
| `should_continue` 永远返回 `"again"`            | 抛 `GraphRecursionError: Recursion limit of 10007 reached without hitting a stop condition`                    |
| 用 `invoke({"n":0}, {"recursion_limit": 3})` | 抛 `GraphRecursionError: Recursion limit of 3 reached`                                                         |
| 节点只返回 `{"n": ...}`（State 里还有别的字段）           | 其他字段**原样保留**：初始 `{"n":0,"tag":"保留了吗"}` → 结果 `{'n': 1, 'tag': '保留了吗'}`                                         |
| 映射表写 `"done": END` 但判断函数返回 `"finished"`     | 找不到对应标签 → 运行时报错（标签必须与映射表一一对应）                                                                                 |

## 一个必须更正的数字

**`recursion_limit` 的默认值是 `10007`，不是 25。**

（25 是早期版本的默认值；当前 `langgraph` 1.x 实测为 10007。）

**这意味着什么**：判断写错导致死循环，**它不会很快停**——会跑到 1 万步才抛异常。

> 手写的 `range(1, 4)` 是**主动设上限**；  
> 框架给的是**一个很大的兜底**，真正的上限要你自己设：`{"recursion_limit": N}`。

# 六、与手写 `agent.py` 的完整对照


| 手写版要自己实现 | LangGraph 的对应物 |
|---|---|
| `for step in range(1, 4)` | 循环边（节点指回自己） |
| `if reply.strip().startswith("{")` | `add_conditional_edges` 的判断函数 |
| `if/elif` 按工具名分发 | 条件边的**映射表**（标签 → 节点） |
| `messages.append({"role": ..., "content": ...})` | 节点返回 dict，框架并入 State |
| `break` | 映射到 `END` |
| `range(1, 4)` 三轮上限 | `{"recursion_limit": N}`（默认 10007） |
| `last_call` 指纹去重（循环外变量） | **没有现成的**——仍需在 State 里加字段自己实现 |
| `try/except` 包住请求 | **没有现成的**——仍写在节点函数内部 |

**结论**：LangGraph 换掉的是**"流程怎么走"**；**"这一步做得对不对、出错了怎么办"仍然是你写**。

# 七、这一版还没有的

1. **没有大模型**——纯计算，`add_one` 不是智能，是算术
2. **没有工具调用**——条件边只有两个标签，真实 Agent 至少需要"调工具 / 直接回答 / 结束"
3. **没有错误处理**——节点里抛异常会直接终止整张图
4. **没有持久化**——`invoke` 跑完 state 就没了
5. **没有可视化**——`graph.get_graph().draw_mermaid()` 能导出图，还没试
6. **没有 `requirements.txt`**——别人克隆下来不知道装什么版本

# 补充：第 18 行与第 20 行深挖（实测）

## 第 18 行 · `compile()` 到底做了什么

### 返回的是什么

```python
graph = builder.compile()
```

实测 `type(graph)` 是 **`CompiledStateGraph`**——一个"编译后的图"对象。

它有这些方法：

| 方法 | 干什么 |
|---|---|
| `.invoke(输入)` | 跑完一次，返回最终 state |
| `.stream(输入)` | 每走一步吐一次中间状态 |
| `.batch([输入1, 输入2])` | 批量跑多条输入 |
| `.get_graph()` | 拿到图的结构（可导出 Mermaid 图） |

### 它做的三件事

| # | 做什么 | 说明 |
|---|---|---|
| 1 | **校验** | 检查结构合法。实测缺入口会抛 `ValueError: Graph must have an entrypoint` |
| 2 | **拍快照** | 把当时的节点表、边表**固化**成一份执行计划 |
| 3 | **产出** | 返回上面那个 `CompiledStateGraph` |

### "拍快照"是什么意思（我原先写成"锁定"，不准确）

编译之后**再对 `builder` 调 `add_node`，不会报错**，只打印一句警告：

```
Adding a node to a graph that has already been compiled.
This will not be reflected in the compiled graph.
```

翻译：**你的改动不会进入已经编译好的那张图。**

- 旧的 `graph` 保持原样（它是**快照**）
- 你可以再 `compile()` 一次，得到一张包含新节点的新图

> 所以准确说法是：**`compile()` 拍下的是一张快照，不是给 `builder` 上锁。**

### 为什么不能直接 `builder.invoke()`

因为 `builder` 只是个**可变草图**，它没有 `invoke` 方法。

**必须先编译**：校验结构 → 固化成执行计划 → 才谈得上"跑"。

## 第 20 行 · `invoke()` 的三个细节

### 细节 1：返回的是"最终 state"，不是节点的返回值

```python
print(graph.invoke({"n": 0}))     # {'n': 1}
```

节点函数返回的是**局部改动** `{"n": 1}`；`invoke` 返回的是**执行结束时的整个 state**。

现在只有一个字段，看着一样；等 State 有五六个字段时，差别就出来了。

### 细节 2：初始 state 必须包含节点会读的字段

| 传入 | 结果 |
|---|---|
| `{"n": 0}` | ✅ `{'n': 1}` |
| `{}`（空 dict） | ❌ **`KeyError: 'n'`** |

**原因**：节点里写了 `state["n"]`，空 dict 取不到就直接抛错。

> **`invoke` 不会帮你补默认值。** `State` 里的类型标注（`n: int`）**不提供默认值**，只是说明"应该是什么类型"。

### 细节 3：State 里没声明的字段会被丢掉

| 传入 | 返回 |
|---|---|
| `{"n": 0, "extra": "会被保留吗"}` | `{'n': 1}` ← **`extra` 没了** |

**原因**：图的"通道"只按 `State` 声明的字段建。**没声明的字段，进不了这张图。**

> 反过来说：**要加一个字段，必须先在 `class State` 里声明。** 这是 LangGraph 和你手写 `messages` 列表最大的区别——手写时你想塞什么就塞什么，这里要先"登记"。

### 可选参数：config

```python
graph.invoke({"n": 0}, {"recursion_limit": 3})
```

第二个参数是配置字典，最常用的就是 `recursion_limit`（默认 10007）。

## 一句话串起这两行

> **`compile()` 是"把草图烧成执行计划"，`invoke()` 是"拿着一份初始数据，把计划从头跑到尾"。**
> 一个管"能不能跑"，一个管"跑一遍"。
